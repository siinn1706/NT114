# Explaining Performance Issues of Cloud Applications From Logs Using Rule Induction and Dempster–Shafer Theory
- openalex_id: W7155397182; version read: publishedVersion (full text); text sha256: 515436a02c93b6f02af93069130f94f05b981ccbc8b23b473ee1b16a7369e808
- Question: explain KPI degradations (disk latency) of ESXi hosts from logs plus metrics, with rules and uncertainty.
- Method: log event types, Random Forest/RFE/permutation importance, RIPPER/CN2 rule induction, Dempster-Shafer rule validation and what-if (SIII-SVI); optional LLM rule annotation (SVII, Fig. 17).
- Data and systems: three private ESXi hosts (A CPU thrashing, B network, C storage) with injected faults, ~3,200 samples at 5 min, ~1,988 features each (SVI, SVI.E); anchor KPI labelled by 97th percentile.
- Modalities: time-series KPIs + event-log distributions.
- LLM: unnamed, only explains rules in the proposed pipeline, not evaluated.
- Baselines: none (qualitative comparison with deviation analysis, RF in SVII.A).
- Metrics: TPR/recall/precision/accuracy for KPI state (Tables 2-5, images, values unseen in text).
- Main results: logs-only RIPPER recall 0.118 (SVI.B, Table 2); fused KPI+log rules 99.6% accuracy on Host A (SVI.C, Table 3); TPR 0.97-0.99 on B and C (Tables 4-5, abstract).
- Artifact: raw data not releasable, code promised as future work (SVII Reproducibility considerations).
- Limitations: logs alone insufficient; statistical vs causal importance; single anchor KPI; subtle contention missed (SVI.D, SVII bias).
- Missing telemetry: logs-only vs fused comparison on Host A is the only handling; no metric-only or degraded-sampling test.
