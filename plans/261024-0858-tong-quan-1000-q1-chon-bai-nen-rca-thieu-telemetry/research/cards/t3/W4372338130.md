## Problem
Localise the faulty service (coarse) and the root-cause metric (fine) after a performance anomaly, using causal structure learning on monitoring metrics (Abstract, Sec.I, Sec.III-A).

## Assumptions
Anomaly already detected; 5 min of data after detection; Prometheus metrics every 5 s; faults raise latency; static DAG over metrics, no time lags (Sec.III-A, Sec.IV-A.2-3, Sec.V).

## Method (data flow / control flow)
Metrics matrix X -> DAG-GNN (VAE with GNN, linear-SEM acyclicity constraint, augmented Lagrangian eta 10, gamma 0.25) -> weighted DAG -> reverse edges, absolute weights -> PageRank (alpha 0.85) -> ranked metrics/services (Sec.III-B, III-C, Eq.1-9). Three modes: latency of all services (coarse), resource metrics of the faulty service (fine), all metrics (Sec.IV-B).

## Modalities
Metrics only: service latency and container CPU, memory, disk read/write, network rx/tx (Sec.IV-A.3, T2).

## LLM role
None.

## Datasets / splits
Sock Shop (13 services, 7 functional) on Kubernetes (1 master + 3 workers), Locust load; Pumba CPU hog, memory leak, network delay per service, 5 min each, 10 min cool-down (Sec.IV-A.1-2). 7 services x 3 anomalies = 21 cases. No train/test split; unsupervised per case.

## Baselines
PC, GES, LiNGAM (causal-learn defaults) each with PageRank. No published RCA system (Sec.IV-A.4).

## Metrics (+denominator)
AC@k = hits in top k / min(k,|Vrc|) (Eq.10); Avg@k = mean of AC@1..k (Eq.11); AC@1, AC@3, Avg@5; 10 runs; ANOVA + pairwise t-test on Avg@5 (Sec.IV-A.5-6). Cases: 7 services per anomaly type (T3 values are multiples of 1/7).

## Main results
- Coarse: average Avg@5 0.5815 vs LiNGAM 0.5143, PC 0.4476; average AC@1 about 0.20 (T3, Sec.IV-B.1).
- Fine in faulty service: AC@3 0.719, Avg@5 0.6681 vs LiNGAM 0.5738; AC@1 0.2476 (T4, Sec.IV-B.2).
- All metrics in all services: average rank about 13 (Fig.10, Sec.IV-B.3); ANOVA p 0.0003 (coarse), 0.0013 (fine).

## Cost
"Tens of seconds" on Sock Shop, rough estimate; 1000 epochs, MLP 2 layers; no GPU stated; scalability untested (Sec.V, Sec.IV-A.4).

## Limitations
All-metric localisation hard; time lags ignored; trace/log calibration and personalised PageRank left as future work; efficiency at hundreds of services unknown (Sec.IV-B.3, Sec.V).

## Threats
One testbed and three fault types (Sec.IV-C external/conclusion); hyperparameter sensitivity reported per anomaly on the same data, defaults chosen from [43] (Sec.IV-C construct, Fig.5, Fig.8); fixed 5-min windows (Sec.IV-C).

## Counter-evidence
- Not best everywhere: coarse network-delay AC@3 0.3857 < PC 0.5714 (T3); fine CPU-hog AC@1 0.2286 < PC 0.4286, memory-leak AC@1 0.2714 < LiNGAM 0.4286 (T4).
- AC@1 only 0.20-0.25 on average; baselines are generic causal discovery, no recent RCA system, no random reference (Sec.IV-A.4, T3-T4).
- 7 cases per type; "10 runs" repeat the same data, so intervals reflect algorithm noise only (Sec.IV-A.4, T3).
- Repo config epochs 500 vs paper 1000; seeds commented out (repo config.py; Sec.IV-A.4).
- Single modality, no missing-telemetry test (Sec.IV-A.3, Sec.V).
